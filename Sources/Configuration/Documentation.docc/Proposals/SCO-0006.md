# SCO-0006: Integer raw value conversions for any BinaryInteger

Extend the automatic `RawRepresentable` integer conversions to enums and types whose raw value is any `BinaryInteger`, not only `Int`.

## Overview

- Author(s): [David Retegan](https://github.com/Dave861)

- Related links:

### Introduction

Generalize the integer-based `ConfigReader` and `ConfigSnapshotReader` overloads from `RawRepresentable<Int>` to `RawRepresentable` where `RawValue: BinaryInteger`, using exact conversions in both directions.

### Motivation

<doc:SCO-0004> introduced `ExpressibleByConfigInt` and documented that integer-based enums don't need to conform to it explicitly:

> If your type is an integer-based enum, you don't need to explicitly conform it to `ExpressibleByConfigInt`, as the same conversions work for types that conform to `RawRepresentable` with an `Int` raw value automatically.

That only holds for `Int` raw values. Enums backed by `UInt8`, `UInt16`, `Int32`, and other integer types are common, especially in networking and protocol code where the raw value mirrors a wire format:

```swift
enum LogLevel: UInt8 {
    case trace = 0, debug, info, warning, error
}
```

Today, the following doesn't compile because no overload matches:

```swift
let level = config.int(forKey: "log.level", as: LogLevel.self, default: .info)
// error: no exact matches in call to instance method 'int'
```

Adopters have to either change the raw type to `Int`, which may not be possible when it's shared with other code, or add a manual `ExpressibleByConfigInt` conformance that repeats the conversion by hand.

### Proposed solution

Every integer accessor that accepts `as: Value.Type` for `RawRepresentable<Int>` today accepts any `RawRepresentable` whose `RawValue` conforms to `BinaryInteger` instead. No new methods are introduced, and existing `Int`-backed enums keep working unchanged.

```swift
enum LogLevel: UInt8 { case trace = 0, debug, info, warning, error }
enum Port: UInt16 { case http = 80, https = 443 }

let level = config.int(forKey: "log.level", as: LogLevel.self, default: .info)
let port = try config.requiredInt(forKey: "server.port", as: Port.self)
let levels = config.intArray(forKey: "log.levels", as: LogLevel.self)
```

Configuration values are still stored and read as `Int`. Conversion to and from the raw value uses exact initializers, so values are never silently truncated or wrapped:

| Configured value | Raw type | Result |
|---|---|---|
| `2` | `UInt8` | `LogLevel.info` |
| `-1` | `UInt8` | Conversion error |
| `300` | `UInt8` | Conversion error |
| `7` | `UInt8` | Conversion error (no matching case) |

A conversion error behaves exactly like an existing conversion error, such as an unknown case of an `Int`-backed enum. Non-throwing methods return `nil` or the default value, throwing methods throw, and the error is reported through the access reporter.

### Detailed design

#### Constraint

The generated overloads in `ConfigReader+methods.swift.gyb` and `ConfigSnapshotReader+methods.swift.gyb` change from:

```swift
public func int<Value: RawRepresentable<Int>>(
    forKey key: ConfigKey,
    as type: Value.Type = Value.self,
    // ...
) -> Value?
```

to:

```swift
@_disfavoredOverload
public func int<Value: RawRepresentable>(
    forKey key: ConfigKey,
    as type: Value.Type = Value.self,
    // ...
) -> Value? where Value.RawValue: BinaryInteger
```

This applies to all of the integer accessors that currently have a `RawRepresentable<Int>` overload: `int`, `requiredInt`, `intArray`, `requiredIntArray`, `fetchInt`, `fetchRequiredInt`, `fetchIntArray`, `fetchRequiredIntArray`, `watchInt`, `watchRequiredInt`, `watchIntArray`, and `watchRequiredIntArray`, including the `default:` variants. In `Scripts/gyb_utils.py`, the `RawRepresentable<Int>` entry of `int_convertible_types` gains a `where` clause, and the generated sources are regenerated.

#### Conversions

Reading (configuration `Int` to `Value`):

```swift
guard let rawValue = Value.RawValue(exactly: int),
      let value = Value(rawValue: rawValue)
else {
    throw ConfigError.configValueFailedToCast(name: ..., type: "\(Value.self)")
}
```

Writing back for access reporting (`Value` to `Int`):

```swift
guard let int = Int(exactly: value.rawValue) else {
    throw ConfigError.configValueFailedToCast(name: ..., type: "Int")
}
```

#### Values that can't be represented as `Int`

A value read from a provider always started out as an `Int`, so converting it back for reporting always succeeds. The only way to get a value that doesn't fit is a caller-provided default, for example a `UInt64`-backed case with a raw value above `Int.max`. In that case, the method still returns the default value, and the failure is reported through `AccessEvent.conversionError`.

### API stability

- `ConfigReader` and `ConfigSnapshotReader` API: the affected overloads keep their names and parameters. Their generic constraint is strictly broader, so every call that resolves to a `RawRepresentable<Int>` overload today still resolves to the new overload with the same behavior.
- `ConfigProvider` API: unchanged. Providers continue to store and return `Int`.
- Existing config provider implementations: unaffected.
- Existing users of `ConfigReader`: without further changes, a type that conforms to `ExpressibleByConfigInt` and is also `RawRepresentable` with a non-`Int` integer raw value (for example `enum E: UInt8, ExpressibleByConfigInt`) would match both overloads, producing an "ambiguous use" error where it resolves to the `ExpressibleByConfigInt` overload today.

  To avoid this, the `RawRepresentable` overloads are marked `@_disfavoredOverload`, so the `ExpressibleByConfigInt` overload always wins when a type conforms to both. This keeps today's behavior for such types, and also resolves the existing ambiguity for types that are both `RawRepresentable<Int>` and `ExpressibleByConfigInt`.

### Future directions

- The same generalization could apply to `RawRepresentable<String>` with other `StringProtocol` raw values (for example `Substring`), if there's demand.

### Alternatives considered

- **Constrain to `FixedWidthInteger`.** This covers the motivating cases and gives access to `.min` and `.max`. However, the implementation only needs `init?(exactly:)`, which every `BinaryInteger` provides. Values of arbitrary-precision integer types that don't fit in `Int` fail conversion the same way an out-of-range `UInt64` does, so the narrower constraint doesn't add safety.
- **Tie-breaking overloads instead of `@_disfavoredOverload`.** Generating an extra overload constrained to `RawRepresentable & ExpressibleByConfigInt` for each integer accessor also resolves the ambiguity, but adds one method per accessor to the generated sources for the same result.
- **Truncating or clamping conversions** (`init(truncatingIfNeeded:)`, `init(clamping:)`). Rejected because they silently turn an invalid configuration value into a different, valid-looking case.
- **Trapping on out-of-range defaults.** Rejected because a default value is expected to always be usable, and a crash in configuration reading is disproportionate.
- **Status quo.** Adopters keep writing manual `ExpressibleByConfigInt` conformances for non-`Int` enums, and the documentation's promise about integer-based enums stays `Int`-only.
